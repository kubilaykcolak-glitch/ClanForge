## 3. Missions system (personal + clan)

### 3.1 Personal missions (`80b4e5d`, refined in `3f2b5e6`)

- **Storage:** `/profiles/{uid}/missions_daily/{YYYY-MM-DD}` (3 missions
  inline) and `/profiles/{uid}/missions_weekly/{YYYY-W##}` (1 mission
  inline)
- **Pool:** Static templates in `src/lib/missions.ts`. 5 daily + 4 weekly
  templates spanning `daily_login`, `post_create`, `tournament_register`,
  `tournament_match_win`. Each template snapshots its reward values into
  the per-user doc at generation time so future pool tuning never
  retroactively changes rewards already promised.
- **Generation:** Lazy, deterministic per-user shuffle seeded by
  `uid:dateKey` (FNV-1a + Mulberry-style PRNG). Race-safe via Firestore
  transaction. Generated by **either** `getDashboardMissions` OR
  `trackMissionProgress` — whichever fires first.
- **Rewards:** Personal XP + clan XP contribution (if user is in a clan).
  Reward amounts are re-derived inside `awardXp` / `awardClanXp` from the
  server-only-written doc — caller cannot supply amounts.

### 3.2 Clan missions (`f44c229`)

- **Storage:** `/clans/{clanId}/clan_missions_daily/{YYYY-MM-DD}` and
  `/clans/{clanId}/clan_missions_weekly/{YYYY-W##}`
- **Pool:** Static templates in `src/lib/clan-missions.ts`. 5 daily + 6
  weekly templates.
- **Action pool — deliberately high-effort and externally validated:**
  - `member_active_day` (dedup per-uid-per-day via `lastClanActiveDate`
    on profile)
  - `tournament_match_win`
  - `tournament_solo_streak` (fires when a member's win-count in one
    tournament hits 3)
  - `tournament_clan_squad` (fires when 3+ clan members in same
    tournament)
  - `tournament_top_place` (top-3 placements)
  - `tournament_run_complete` (member-created tournament finalises)
- **No spammable engagement actions** — no posts, likes, comments.
- **Contributors map:** Each mission carries a `contributors` map
  (`{ [uid]: count }`). On completion the clan gets `clanXpReward` once,
  and **every** contributor gets `memberXpReward` once
  (`clan_mission_contribute` XP reason, `once_per_target`).

### 3.3 Mission tracking fire points

All fire points are awaited inside their parent server action's try block
so request context (session + AsyncLocalStorage) propagates correctly.

| Action | Fire point | Wired in commit |
|---|---|---|

| `tournament_register` (free) | `registerForTournament` | `80b4e5d` / `3f2b5e6` |
| `tournament_register` (paid) | `confirmPaidParticipant` via Stripe webhook (try/catch + AsyncLocalStorage) | `3f2b5e6` |

| `tournament_match_win` (clan) | `reportMatchResult` | `f44c229` |

### 3.4 Bugs fixed in `3f2b5e6`

This commit is critical context — without it, missions would silently
fail in production scenarios.

1. **Lazy-gen gap:** `trackMissionProgress` / `trackClanMissionProgress`
   only acted on EXISTING docs. If a user registered for a tournament
   before opening the dashboard, their daily doc didn't exist and the
   increment was dropped. Now both functions lazy-generate via the same
   race-safe transaction pattern.
2. **Fire-and-forget context loss:** `.then(...)` chains run AFTER the
   parent server action returns. Session context may be cleaned up by
   then, causing `getSessionUid()` inside the chain to fail silently.
   All chains converted to awaited calls inside try/catch.
3. **daily_login dedup migration:** Previously gated by "did THIS
   getDashboardMissions call generate the doc?". After fix #1 the doc
   may already exist from a different fire point. Migrated to
   profile-based `lastDailyLoginDate` dedup (same pattern as
   `lastClanActiveDate`).
4. **Webhook session bypass:** Stripe webhooks have no session cookie.
   Added `src/lib/webhook-context.ts` (AsyncLocalStorage flag set inside
   the verified-signature route handler). `requireAuthContext()` in
   `server-auth.ts` accepts either a session OR webhook context. Applied
   to `awardXp`, `awardClanXp`, `awardClanXpForMember`,
   `trackMissionProgress`, `trackClanMissionProgress`.

### 3.5 Mission XP reasons (in `xp.ts` / clan-xp)

| Reason | Where amount comes from |
|---|---|
| `daily_mission_complete` | Snapshotted `xpReward` on `/profiles/{uid}/missions_daily/{key}` |
| `weekly_mission_complete` | Snapshotted `xpReward` on `/profiles/{uid}/missions_weekly/{key}` |
| `clan_mission_contribute` | Snapshotted `memberXpReward` on `/clans/{clanId}/clan_missions_*/{key}` — recipient verified in `contributors` map |
| `clan_mission_complete` (clan-XP) | Snapshotted `clanXpReward` on the clan mission doc |

**Caller never supplies amounts.** `awardXp` and `awardClanXp` re-read the
server-only-written doc to derive the actual amount. Hard caps: 1000
personal XP / 500 member XP / 1000 clan XP per call.

## 4. Security model — current state

### Audit fixes (in `80b4e5d` and earlier session work)

| Class | Fix applied |
|---|---|
| **IDOR (caller-supplied UID):** ~15 server actions | `sessionUid !== uid → Forbidden` |
| **Admin layout bypass** | `await getAdminUid()` at top of action — `createChallenge`, `updateChallengeStatus`, `getAllChallenges`, `createSeason`, `updateSeasonStatus`, `markPrizePaid` (two-layer) |
| **Caller-supplied identity** | `createCheckoutSession` reads `displayName`/`avatarUrl` from Firestore |
| **Cross-reference validation** | `finalizeTournament` validates `winnerUserIds` are real registered participants |
| **Numeric amount inflation** | `trackChallengeProgress` hardcodes `safeAmount = 1` |
| **Cross-user server-to-server** | `awardXp`/`awardClanXp`/`trackMissionProgress`/`trackClanMissionProgress` use session-exists-only gate (commented) |
| **Firestore rules** | Tournament `create` enforces `creatorId == request.auth.uid` |

### New surface from missions (audited)

- **Read actions** (`getDashboardMissions`, `getClanMissions`): full uid
  equality + clan membership check
- **Track actions:** session-exists gate (or webhook context), enum
  allowlist on `action` param, contributor uid membership check (clan)
- **All mission XP awards:** server-derived amount from snapshot doc

### Firestore rules — new subcollections

```
/profiles/{userId}/missions_daily/{dateKey}      // owner read, server-only write
/profiles/{userId}/missions_weekly/{weekKey}     // owner read, server-only write
/clans/{clanId}/clan_missions_daily/{dateKey}    // member read, server-only write
/clans/{clanId}/clan_missions_weekly/{weekKey}   // member read, server-only write
```

## 7. Open / known follow-ups

Not blockers, but candidates for next sessions:

1. **`ClanLevelBadge` → `RankChevron` swap site-wide.** Deferred because
   it's used in many surfaces. Once stable, one PR could unify it.
2. **Mid-tier hero treatments.** Tournament detail page hero
   (`/tournaments/[id]`) hasn't received the arena-gradient-border +
   aurora default banner pass yet — only inherits via children
   (registration aside, finalize, prize claim). Same for
   `dashboard/onboarding`.
3. **Mobile responsive review** of the new `.arena-cta` sizes. Most are
   `padding: 11px 20px / fontSize: 13`. Have been tested via build but
   not manually on actual mobile screens.
4. **Empty / loading / error states on missions widgets.** Current
   implementation has them, but copy may need product review.
5. **Backfill consideration.** The `3f2b5e6` mission bug fixes are
   forward-looking only. Users with `progress=0` daily docs from before
   the fix won't be retroactively credited for past actions. If anyone
   reports this, the fix is: register/win one more thing today, which
   will increment from 0 → 1 → completed.
6. **Decorative branding tiles** still use `background: var(--accent)`
   directly (CF logo squares, user-initials avatars). If the user wants
   a deeper visual sweep, swapping these to the indigo→magenta gradient
   would unify everything 100%. Currently kept simple to avoid
   over-applying the gradient.

## 8. How to resume

### If the user reports a bug
1. Reproduce locally (check session state — is the user logged in? Is
   the doc generated today?).
2. Check `docs/security-guidelines.md` Audit Log — has this class
   already been seen?
3. Check `docs/HANDOFF.md` §3.4 — known mission edge cases.

### If the user requests a new feature
1. Invoke `superpowers:brainstorming` skill for the design phase.
2. Read `docs/security-guidelines.md` §2 Pre-Implementation Checks.
3. Read `docs/ui-design-guidelines.md` §3 Pre-Implementation Checks.
4. Run during-implementation checklists from both docs as code is
   written.
5. Run post-implementation verification before commit (attack
   simulation + UI consistency).

### If the user requests a UI polish pass
1. Reuse the existing utility classes documented in §5.2 — do not
   introduce parallel ones.
2. Reuse the existing UI primitives in §5.3 — do not duplicate.
3. Follow the Phase 4 pattern: foundation utility first, then sweep
   surfaces, then verify build.

### If the user requests another security audit
The `docs/security-guidelines.md` audit log (29 entries) plus this
handoff covers everything that's been done. Anything new would extend
that log with new entries.
